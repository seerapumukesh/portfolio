What a 45% query speedup actually took

May 2026 · Mukesh Seerapu

"Improved query performance by 45%" is the kind of line that shows up on a resume without the work behind it. In practice it wasn't one change — it was three separate, smaller fixes that compounded, found by actually reading query profiles instead of guessing.

1. Clustering keys that matched real filter patterns

The original migration copied table structures over close to as-is from SQL Server. Snowflake's micro-partitioning rewards clustering on the columns queries actually filter and join on — in this case, date and a regional key — which cut the amount of data scanned per query significantly on the largest fact tables.

2. Warehouse sizing per workload, not one size for everything

Running ad-hoc analyst queries and scheduled dbt transformation jobs on the same warehouse meant either paying for idle compute or queuing behind long-running jobs. Splitting into separate warehouses sized for each workload, with auto-suspend tuned aggressively, removed most of the queuing delay analysts were seeing.

3. Materializing the transformations that got queried the most

A handful of dbt models were being recomputed as views on every query because they were built for correctness first. Converting the ones with heavy read traffic into incremental tables — refreshed on schedule instead of on every read — moved that cost out of the interactive query path entirely.

What mattered most

None of these three individually was dramatic. What made a visible, reportable difference was doing all three together and measuring before and after with the same representative query set, rather than assuming any single change was "the fix."
