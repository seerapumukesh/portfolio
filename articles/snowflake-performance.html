Before you scale the warehouse, find out where the time actually goes

Mukesh Seerapu

A pipeline slowing down usually gets the same first reaction: bump the warehouse size. Sometimes that's right. Often it's an expensive way to make a bad query run on more expensive compute, and the actual bottleneck never moves. The fix that works is boring and always the same first step — break the total runtime into its stages before touching anything.

What the breakdown actually looked like

On one recurring batch, the total run time was split roughly like this: 8 minutes for source extraction, 3 minutes writing to blob storage, 4 minutes on the Snowflake COPY, 38 minutes on a dbt mart model, and 2 minutes reconciling counts. Without measuring the stages separately, the instinct is to blame "Snowflake" as a whole and scale the warehouse. With the breakdown, it's obvious the mart model — one specific dbt model — was responsible for 80% of the runtime, and everything else was already fine.

Where the 38 minutes actually went

Once a single model is the target, the Snowflake query profile tells you which of a handful of usual suspects is responsible: scan volume, a join exploding row counts, spilling to disk, queueing behind other workloads on the same warehouse, or the model simply recomputing something on every run that didn't need to change. In this case it was a mix of two: the model was fully rebuilding a large table on every run instead of processing only what changed, and it shared a warehouse with ad-hoc analyst queries that created contention during the overlap window.

The fixes, in order of what actually moved the number

  • Converted the model to an incremental materialization keyed on the source's updated-timestamp, so only changed rows were reprocessed
  • Split ingestion/transformation workloads onto a separate warehouse from ad-hoc BI queries, removing the contention
  • Enabled auto-suspend so idle compute stopped costing money between runs, with auto-resume so scheduled jobs weren't affected
  • Reviewed whether clustering would help — and didn't add it, since pruning on the filtered columns was already reasonable and clustering has a real maintenance cost on a table that size

The part worth remembering

Warehouse size was never the actual lever here. Scaling compute on a query that's recomputing an entire table from scratch just makes an inefficient query finish a bit faster while still doing unnecessary work, and it makes that mistake more expensive, not less present. The breakdown is what turns "the pipeline got slow" into a specific, fixable claim — and it's the same first step regardless of what the actual bottleneck turns out to be.
