Designing Slowly Changing Dimensions that survive an audit

Mukesh Seerapu

On a regulated banking data platform, "what did this member's record look like on a specific date" isn't a hypothetical question — it's the kind of thing an auditor asks, or a dispute-resolution team needs answered exactly, not approximately. If your warehouse only keeps the current state, you don't have an answer. That's the whole case for SCD Type 2, and also where most implementations quietly go wrong.

Detecting a real change, not a formatting difference

The first problem is deciding whether a row actually changed. Comparing every tracked column individually gets unwieldy fast, so a cleaner approach is hashing the tracked attributes into a single value — concatenate the columns you care about, coalesce nulls to a consistent placeholder, and hash the result. A new row's hash either matches the current version or it doesn't. No column-by-column diff logic scattered across every model.

dbt snapshots vs. custom SCD logic

dbt's built-in snapshot feature handles the mechanical part of Type 2 well — it tracks effective and expiration dates automatically once you give it a strategy and the columns to check. It's the right default. The case for writing custom SCD logic instead shows up when you need tighter control than a snapshot gives you: backdated corrections that need to slot into an already-closed date range, enterprise-specific effective-dating rules, or performance tuning on a dimension too large for a snapshot's default behavior. Start with the built-in snapshot. Only reach for custom logic when a specific requirement forces it.

The fact table needs the same discipline

Dimension history is half the problem. Fact loading has to be safe to replay, which means a MERGE keyed on a stable business identifier (a transaction ID, not a surrogate key generated on load) — update if the source's own updated-timestamp is newer than what's already there, insert if it doesn't exist. Re-running a batch after a partial failure shouldn't double-count a single transaction, and this pattern is what makes that true.

The part that actually gets you through an audit

None of the above matters if a bad batch can quietly corrupt history. The pattern that held up: capture a fixed upper boundary for the batch window at the start of extraction (not an open-ended "greater than last watermark," since new changes can land mid-run and create an ill-defined batch), validate the landed data before it touches anything downstream, and only advance the watermark after reconciliation — source count vs. staged count vs. inserted/updated count — actually passes. A failed validation routes to quarantine instead of the pipeline. On the next run, nothing has silently drifted, and the watermark tells you precisely where the pipeline stands. That combination — hash-based detection, discipline about which tool does the SCD tracking, idempotent fact loads, and a watermark that can't advance on unverified data — is what actually survives someone asking "prove this number was right on that date."
