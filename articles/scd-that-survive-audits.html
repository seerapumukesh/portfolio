Designing Slowly Changing Dimensions that survive audits

March 2026 · Mukesh Seerapu

Regulated financial data has a habit of exposing lazy dimension modeling. A customer's address changes, a credit tier gets recalculated, an account status flips — and six months later an auditor asks what the record looked like on a specific date. If your warehouse only ever holds the current state, that question has no good answer.

Why Type 2 earns its complexity

SCD Type 2 keeps every version of a row with effective and expiry dates, so a report run "as of" a past date reconstructs exactly what was true then. It costs more storage and more transformation logic than simply overwriting rows, but for anything touching compliance reporting, that cost is the whole point — it's what makes the history defensible.

Where it actually breaks in practice

  • Late-arriving source data that needs to be inserted retroactively into an already-closed date range
  • Multiple source systems disagreeing on when a change "actually" happened
  • Surrogate keys that aren't stable across a full reload, silently breaking history joins
  • Tests that check row counts but never check that effective-dated ranges don't overlap

What held up under review

The pattern that survived an actual compliance review combined dbt snapshots for the mechanical Type 2 tracking with explicit tests asserting no overlapping date ranges per natural key, plus a small reconciliation job that flagged any record where the source system's own "last modified" timestamp didn't line up with when we recorded the change.
