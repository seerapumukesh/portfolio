Airflow vs. cron: what actually changes at scale

Mukesh Seerapu

Cron can start a script at a time. It does not track dependencies or recovery. On an annuities data platform coordinating dozens of daily batch jobs across a warehouse, a lake, and a couple of NoSQL stores, "start a script at a time" stopped being enough well before we hit 30 jobs — not because cron broke, but because nothing about it could answer "which job failed, why, and what do I need to rerun."

What a job actually needs to do

A single daily pipeline run isn't one step, even if it feels like one script. In practice it's: confirm the source is ready, read the last successful watermark, capture a fixed upper boundary for this run, extract only the incremental slice, land it, validate it, route it to either processing or quarantine, transform it, reconcile source counts against what landed, and only then commit the new watermark. Cron can trigger the first step. It has no concept of the other nine, which means all that sequencing and error handling ends up hand-rolled inside the script itself — and hidden from anyone who isn't reading the code.

The shift that mattered

Airflow's dependency graph made each of those steps a visible, individually retryable task instead of a lump of logic inside one script. When the transform step failed at 2am because an EMR step timed out, the DAG run showed exactly which task failed — not "the job failed," but which of the nine steps, with its own logs. Rerunning meant retrying that one task, not re-extracting data that had already landed successfully. That's the actual value: not the scheduling, but the fact that failure has a precise location and a precise fix.

What showed up in day-to-day operation

  • Backfills became a normal, supported operation instead of a manual script someone had to write under pressure
  • Retries with backoff were configuration, not something every script author had to remember to implement
  • A dependency graph made it obvious which downstream jobs a delayed upstream source would actually affect
  • SLA and failure alerting pointed at a specific task, not a generic "pipeline X failed" page at 2am

Where cron is still the right answer

None of this is a reason to run Airflow for three independent jobs with no shared dependencies — that's real infrastructure to operate (a scheduler, a metadata database, workers) for a problem cron already solves. The switch earns its cost specifically when job count and inter-dependency both grow past what fits in one person's head, and when "which task failed and what do I rerun" becomes a question you're answering multiple times a week instead of once a quarter.
